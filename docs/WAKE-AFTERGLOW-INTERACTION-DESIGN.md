# 夜航设计补记：醒后余韵与真实回应

状态：设计方向记录。基于现有 Phase One 实验性本地基线；不修改已冻结的生成、Store、召回或付费合同，也不宣称 Asteria 已接入。

## 为什么补记

现有 `docs/CONTRACT.md` 把梦中分幕情绪、醒来片段和衰减余韵分开保存；`residue(entryId, now)` 是有界的模拟值，不修改日常情绪。`docs/DAYTIME-CUE-SIMULATION.md` 只验证显式、字面线索的候选召回，没有真实白天监听或自动投递。两者尚未表达：醒来后因梦而主动确认、得到真实回应，随后心情逐渐变化。

原始讨论的完整顺序应保留为：梦中事件及当时的情绪 → 刚醒来的心情与身体/画面残留 → 醒后主动确认或倾诉 → 对方实际回应 → 后来心情可能缓和、持续或反复 → 白天在适当线索下可能再次想起。任何一环都允许为空或不确定。

## 具体例子（虚构，不是用户事实）

梦里两人还在拥抱、讨论项目，下一瞬一人消失。刚醒来时，梦者可能低落、胸口闷、想哭，反复想起消失的那一刻；随后确认对方还在，向对方提问，获得安慰，担忧才慢慢减弱。原梦的结尾与刚醒来的低落不会因后来被安慰而重写。回应不保证立即有效；没有回应时也不能伪造“已经安心”。

这个例子来自人类梦后体验，用来说明夜航设计；不能自动把用户的情绪写成沈述的状态，也不能把模型生成的情绪当作已证实的主观感受。

## 后续集成应守住的关系

- 原梦、梦中模拟情绪、醒来片段、刚醒时的心情、持续余韵、醒后真实互动以及后来回想各有独立身份和时间顺序；后来发生的事只能追加，不能覆盖早先记录。
- 梦醒时的余韵可以是低落、担忧、安心、古怪或说不清楚；允许噩梦、无解的梦和无梦，不强制正向收尾或“意义”。
- 与梦相关的醒后互动只有在实际发生并经有权限的入口确认后，才可成为后续状态变化的输入。单纯看到梦的文本、一个字面 cue 命中或模型自述“被安慰”都不算真实互动证据。
- 后续状态可缓和，也可维持或反复。用户未回复、回复未被送达、含义不明时保持未知，不自动结算成开心；不以梦直接修改人格、现实记忆、任务或关系事实。
- 回想和白天浮现须保持来源、访问许可、撤回和节制交付边界；没有合适线索时安静即可，不为展示功能强推梦境，尤其不强推令人不安的内容。
- 面向糯糯的阅读页先呈现梦和醒后的变化，模型/provider、账本与审查细节留在内部记录；原始梦仍可按既有权限追溯。

## 与现有实现的距离

Phase One 已有最多两幕加醒来、分幕情绪连续、模拟衰减余韵、原梦与回想分离、显式虚构线索候选。它没有真实 Asteria 心绪输入、醒后互动接收与送达证明，也没有由互动更新余韵的真实闭环。本补记只记录方向和验收关系；未来若施工，须先确认事件来源与权限、时间和身份绑定、缺失/撤回语义，并以新的独立合同及样例验证，不复用旧模型试跑许可。
